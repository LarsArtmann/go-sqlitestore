## Status legend

Every label answers ONE question: does working code exist — and if not,
why not?

| Status                    | Meaning                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 🟢 `FULLY_FUNCTIONAL`     | Works as intended, exercised by tests or daily use.                                                                 |
| 🟡 `PARTIALLY_FUNCTIONAL` | Ships but has known gaps, edge-case bugs, or missing pieces.                                                        |
| 🔴 `BROKEN`               | Present in code but failing. Keep BROKEN nameable — "zero BROKEN rows" is itself information.                       |
| 🔵 `DISABLED`             | Code exists and is correct, but execution is externally switched off. A switch, not a fix — never fold into BROKEN. |
| ⚪ `PLANNED`              | No code yet; genuinely next on the build path.                                                                      |

## Explicitly out of scope (by design, not demand-gated)

| Non-feature                                 | Reason                                                                                                                  |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Application/domain types (tools, findings…) | The cardinal rule: consumers own schemas; this package owns mechanics only (`doc.go:6-9`)                               |
| Read-path wrappers / query builders         | `DB()` hands back the raw handle for reads; consumers own their query surfaces                                          |
| Migrations auto-run on `Open`               | Deliberate: callers pass their own list because state and cache databases carry different schemas (`engine.go:101-103`) |
